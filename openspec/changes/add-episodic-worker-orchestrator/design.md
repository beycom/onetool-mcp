## Context

The main Codex conversation is useful for user coordination but is a poor place
to accumulate every tool result and implementation detail from a long task. The
core idea is to keep coordination continuous while making substantive execution
episodic: every episode uses a fresh worker thread and carries forward only a
small record of current operational truth.

The context is the heart of the design. It must be complete enough that a fresh
worker can continue effectively, small enough to read in full, and structured
enough that the MCP runtime can process it deterministically. It is state, not a
transcript, event log, knowledge database, or compressed copy of prior messages.

## Goals / Non-Goals

**Goals:**

- Keep the user in one normal main conversation while substantive work happens
  in fresh Codex app threads.
- Give each worker all current context without replaying earlier worker messages.
- Preserve the highest-value state: goal, success conditions, current progress,
  next actions, blockers, durable knowledge, unresolved questions, and useful
  project-file references.
- Keep the context interface small: automatic whole-object read and one
  whole-object replacement.
- Make formatting, validation, allowed repair, revisioning, and persistence
  deterministic MCP runtime behavior.
- Keep the stored context within a simple configurable file size measured in KB.
- Preserve the last valid context when an episode or write fails.

**Non-Goals:**

- Conversation replay, transcript search, embeddings, or long-term memory.
- Context section queries, search, patches, upserts, IDs, or merge semantics.
- Model-driven cleanup presented as deterministic repair.
- Automatic semantic truncation, summarization, or compaction.
- A session artifact store, console outbox, scheduler, concurrency, recursion,
  automatic retry, warm-process optimization, or detailed telemetry.
- A new interactive CLI or replacement chat client.

Deferred ideas are described in `next.md`; they are not v1 requirements.

## Decisions

### 1. One fresh worker thread per episode

The explicitly invoked `episodic-orchestrator` skill keeps the main agent focused
on coordination. It passes the current user request and one explicit execution
object to
`worker.run(prompt=..., execution=..., session_id=..., model=..., effort=...)`,
then relays the worker's terminal result or request for input.

The strict v1 execution object contains exactly `cwd`, `approval_policy`, and
`sandbox`. `cwd` is the absolute current project directory,
`approval_policy` is always `never`, and `sandbox` is `read-only` or
`workspace-write`. The adapter disables network access and limits
`workspace-write` to `cwd`. Other policies fail before `thread/start`; v1 has no
mid-turn approval bridge or permission-profile translation.

The first call omits `session_id`. The MCP creates an opaque session ID under the
current project-state root and returns it. The orchestrator retains that ID as its
only session state and supplies it on every later call in the same main
conversation. A supplied ID must already exist under the current project-state
root; otherwise the call fails rather than creating or guessing a session. There
is no implicit "latest session" lookup or automatic cross-conversation reuse.

Each `worker.run` call creates a new Codex app thread and never resumes it. Codex
loads its normal instructions, skills, tools, and configured MCPs for the supplied
working directory and installed configuration. The adapter marks the child
environment, and `worker.run` rejects calls from that environment, so v1 cannot
recurse or fan out.

One dedicated adapter owns the Codex app-server protocol. It initializes each
connection, starts one fresh thread and turn, consumes events through the terminal
`turn/completed`, and returns one normalized worker result to the orchestration
runtime. The adapter is implemented against schemas generated by the installed
Codex version; archived request shapes are evidence, not an API contract. See
`prior-art.md` for the archived implementation review.

Before starting the thread, the adapter validates the explicit execution object,
confirms `cwd` is the current project directory, and maps it to the installed
app-server schema. If that schema cannot represent the requested restrictions,
`worker.run` fails before the worker starts. It never widens the supplied policy.

`worker.run` always returns exactly three fields:

```json
{
  "session_id": "ep-7f3a...",
  "status": "completed",
  "message": "Implemented and verified the requested change."
}
```

| Status | Meaning |
|---|---|
| `completed` | The turn completed and any valid terminal context was committed. |
| `needs_input` | The turn completed; `message` contains one direct question for the user. |
| `failed` | Preflight, startup, protocol, timeout, output validation, or context commit failed. |
| `interrupted` | The active turn was explicitly cancelled or reported interrupted. |

The adapter supplies a strict turn output schema with a worker-authored `status`
of `completed` or `needs_input`, one `message`, and optional complete `context`.
The adapter validates and commits that context, strips it from the public result,
adds `session_id`, and maps runtime failures and interruption. Invalid terminal
output or context is `failed`; absent context preserves the revision. The user's
answer to `needs_input` becomes the next prompt for the same session.

After capturing the terminal payload and committing or preserving context,
the adapter calls the current app-server `thread/delete` method and never resumes
that thread. A deletion failure does not change the episode status or context; the
runtime appends one cleanup warning to `message`, logs the protocol error, and
still never reuses the thread. The adapter checks for `thread/delete` in the
installed version's generated schema before starting any worker.

One worker call is active at a time. This removes the need for merge rules,
leases, conflict resolution, queues, and distributed scheduling.

**Alternative considered:** resume one worker thread. This preserves irrelevant
history and defeats the context boundary.

### 2. Read the complete context; do not search it

At episode startup, the runtime safely loads and validates the complete stored
context and supplies the parsed object to the worker as delimited state data.
The initial episode receives an explicit empty-context marker with revision `0`.
Context data cannot override the current request, project instructions, worker
contract, sandbox, or approvals.

Before `thread/start`, the MCP runs the same safe load, deterministic
normalization, strict validation, reference checks, canonical rendering, and file
size measurement used for writes. Safe but noncanonical YAML is atomically
rewritten in canonical form. Unsafe or unreadable YAML, invalid schema, an
oversized canonical file, or a missing or invalid reference returns `failed` with
the affected field or path and starts no worker. The existing file is otherwise
left unchanged; v1 never guesses, drops content, or resets context automatically.

There is no worker context-read tool in v1 because the complete state is already
present at startup. There is also no section selector or search API. A file small
enough to require search has already violated the design goal, and selective
retrieval would make each worker reconstruct state before it could work.

**Alternative considered:** bootstrap an index and retrieve sections or IDs on
demand. This adds tool calls, selectors, indexing, missing-state risk, and a
second size-control mechanism without solving a demonstrated v1 problem.

### 3. Return at most one complete typed replacement

The worker may include one complete structured `context` object in its strict
terminal output. It never submits raw YAML, YAML fragments, formatting choices,
patch operations, repair instructions, or a separate context tool call.

On a valid `completed` or `needs_input` result, the runtime commits the supplied
context. If the field is absent, the revision does not change. Invalid context,
failure, cancellation, or interruption keeps the committed file unchanged.

This snapshot model makes supersession explicit: the submitted object is current
truth, not an append-only history. It avoids stable IDs, operation ordering,
partial-item validation, compaction commands, and merge behavior.

**Alternative considered:** a separate save tool with staged `replace`, `upsert`,
and `remove` operations. It adds cross-process episode state and more surface than
the single complete v1 file warrants.

### 4. Use a compact schema centered on continuation value

The canonical stored form is:

```yaml
schema_version: 1
revision: 12
goal:
  status: active
  objective: |
    Implement episodic worker orchestration with focused current context.
  success_criteria:
    - Every episode uses a fresh worker thread.
    - Context remains useful and small across repeated episodes.
work:
  summary: |
    The proposal and core context design are complete; delta specs are next.
  next_actions:
    - Write the delta specifications.
    - Define implementation tasks after the specs are reviewed.
  blockers: []
knowledge:
  - kind: decision
    text: |
      Workers submit complete structured state; the MCP renders canonical YAML.
  - kind: constraint
    text: |
      Prior worker conversation is never supplied to a new worker.
questions: []
references:
  - path: openspec/changes/add-episodic-worker-orchestrator/proposal.md
    purpose: Defines the approved v1 scope.
```

The worker-maintained submission omits `schema_version` and `revision`; the
runtime adds them. Every other top-level field is required:

| Field | Contract |
|---|---|
| `goal.status` | `active`, `blocked`, or `complete`. |
| `goal.objective` | The current outcome, not its history. |
| `goal.success_criteria` | Ordered, independently testable completion conditions. |
| `work.summary` | Concise current progress and relevant work in progress. |
| `work.next_actions` | Ordered actions useful to the next worker. |
| `work.blockers` | Current technical or coordination blockers. |
| `knowledge` | Durable `fact`, `decision`, or `constraint` entries with self-contained text. |
| `questions` | Unresolved questions whose answers can change subsequent work. |
| `references` | Existing project-relative files with a short statement of their purpose. |

The schema intentionally has no plan-step graph, item IDs, evidence graph,
retention markers, artifact lifecycle, per-question ownership, or patch paths.
Rationale and provenance that matter can be written directly into a concise
knowledge entry or referenced project file.

### 5. The MCP owns deterministic formatting, validation, and repair

The terminal `context` field accepts a typed object and the MCP applies this
fixed pipeline:

1. Normalize text line endings to LF, remove trailing spaces and tabs, and remove
   surrounding blank lines.
2. Remove blank string-list entries and exact duplicates while preserving the
   first occurrence and submitted order. Deduplicate knowledge by `(kind, text)`
   and references by `(path, purpose)` using the same rule.
3. Normalize project-relative path separators and lexical `.` segments.
4. Validate the strict versioned schema, enums, required nonblank scalar fields,
   unknown-field prohibition, and reference paths. Reference paths must resolve
   to existing regular files inside the project root; absolute paths and escapes
   are rejected.
5. Render canonical YAML with fixed key order, UTF-8, LF line endings, and one
   final newline. The serializer chooses scalar styles consistently and never
   emits comments, aliases, anchors, or custom tags.
6. Measure the canonical encoded bytes and compare them with the configured file
   size.

These are the only repairs v1 permits. The runtime does not infer whether a fact
is stale, combine similar notes, rewrite prose, summarize evidence, or choose
what to discard. Such changes are semantic authorship, not deterministic repair.
If a value remains invalid or the canonical file is too large, the MCP rejects
the result with field-specific errors and exact actual/allowed byte counts.
It never asks the worker to repair YAML because the worker never produces YAML.

**Alternative considered:** ask the worker to compact or repair malformed state.
That makes correctness depend on model behavior and incorrectly describes a
semantic rewrite as runtime-owned maintenance.

### 6. Use one simple KB file-size setting

`tools.worker.context_max_kb` has an accepted v1 default of `16` and is
configurable as a strict positive integer. The runtime accepts a canonical file
only when:

```text
len(canonical_yaml.encode("utf-8")) <= context_max_kb * 1024
```

There is no tokenizer, estimated token count, percentage threshold, reserve,
automatic compaction trigger, or claim that total worker input is bounded by this
value. Instructions, tool definitions, the current user request, and project
files read during the episode remain outside the context file measurement.

The file-size setting is a storage and focus guard, not a model-context budget.
The error reports bytes and configured KB so its result is deterministic on every
platform.

**Alternative considered:** a token budget. Token counts depend on a selected
tokenizer and add accounting complexity without improving the stored-state
contract.

### 7. Commit atomically and keep the last valid state

At successful episode completion, the runtime rechecks the loaded revision,
increments it, renders the terminal context, writes a temporary file beside
`context.yaml`, flushes it, and atomically replaces the committed file. The file
lives at:

```text
episodic-context/<session-id>/context.yaml
```

under OneTool's project-state directory. Direct file editing is not a supported
write interface; the YAML is human-inspectable. On load, structurally valid but
noncanonical state is normalized and rewritten by the MCP. Unsafe YAML or state
that cannot pass strict validation is rejected rather than guessed at.

Atomic replacement protects against torn writes. Revision checking protects
against unexpected stale submissions even though v1 serializes worker calls. A
worker that may already have changed project or external state is never replayed
automatically after failure.

## Risks / Trade-offs

- **A whole snapshot repeats unchanged state in one tool call.** → The file is
  capped at 16 KB and written at most once per successful episode; simplicity is
  more valuable than optimizing this small transfer.
- **A worker may omit useful state from its replacement.** → The fixed schema and
  worker instructions emphasize continuation value; MCP validation ensures
  structure but deliberately does not pretend to judge semantic completeness.
- **Rejecting oversized state cannot identify what is least important.** → Return
  exact size information and preserve the prior state. Do not silently truncate
  or label model judgment as deterministic repair.
- **A failed side-effecting episode does not advance context.** → Preserve the
  last valid state and let the next fresh worker inspect actual project state
  before deciding how to continue; never replay automatically.
- **Project files referenced by context can later move or disappear.** → Validate
  references at submission time. A later missing reference is reported when the
  next episode loads context and does not grant access outside the project.
- **The orchestrator can become a second execution agent.** → Its skill contract
  allows only coordination and `worker.run`; substantive inspection, planning,
  edits, and verification remain worker responsibilities.

## Migration Plan

This is a new explicitly invoked feature with no existing persisted schema to
migrate. Implement the strict schema and tools together, distribute the skill,
and enable the workflow only when invoked. Rollback removes the skill and worker
configuration; existing context files remain inert project-state data.

No compatibility aliases, legacy context keys, or schema fallbacks are provided.

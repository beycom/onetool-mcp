## Why

Today's install funnel is broken end to end. Docs recommend `uv tool install onetool-mcp` with no host-managed uv bootstrap, provide no command that prints ready-to-paste MCP client JSON (every doc hand-writes a placeholder path like `/Users/yourname/.onetool/onetool.yaml`), and document only Claude Code despite OneTool working with "any MCP client." Separately, the pieces of a first-run flow — package install, `onetool init`, `onetool init validate`, secrets placement, overwrite behavior, and startup failure guidance — exist in isolated docs sections with no single contract tying them together: `onetool init` run a second time non-interactively silently discards previously-selected extensions with no prompt and no `--force` opt-out, and a bad `--secrets <path>` at server startup is silently swallowed (server starts with zero secrets loaded, no error) instead of failing with an actionable message. The maintainer has flagged install as "a huge pain-point" for V3. This change makes the funnel: install → init → mcp-config → validate a single, repeatable, testable contract.

## What Changes

- Add a `curl … | sh` (macOS/Linux) and `irm … | iex` (PowerShell/Windows) bootstrap installer that **wraps `uv`, never replaces it**: detects the platform, installs `uv` if missing, runs `uv tool install 'onetool-mcp[<extras>]'`, runs `onetool init`, and prints ready-to-paste MCP client config. Hosted on the official docs domain and mirrored via a git-tag-pinned GitHub raw URL for reproducible installs; ships with a published sha256 checksum and documented inspect-before-run instructions. `uv tool install onetool-mcp` remains the documented manual path — the bootstrap is additive, not a replacement.
- Add `onetool init mcp-config [--client claude-code|claude-desktop|cursor|vscode] [--config PATH] [--secrets PATH]` — prints ready-to-paste MCP client JSON with **resolved, absolute paths** (config path, secrets path if it exists, and the resolved absolute path to the `onetool` executable itself via `PATH` lookup) instead of placeholders. Supports all four named clients with their correct on-disk config format (`mcpServers` vs VS Code's `servers` + `"type": "stdio"`) and correct target file location per client/OS. Defaults to printing all four when `--client` is omitted, forming the source content for a new "Other clients" docs section.
- **BREAKING (CLI contract):** `onetool init` (non-interactive / non-TTY invocation) becomes idempotent by default — if the target `onetool.yaml` already exists, it now exits 0 as a no-op instead of silently overwriting it with an empty `include:` list. A new `--force` flag restores the previous unconditional-overwrite behavior (and, in interactive/TTY mode, skips the existing overwrite confirmation prompt).
- Fix a silent-failure gap at server startup: a `--secrets <path>` that does not exist is currently swallowed (`ot.config.secrets.get_secrets` never passes `explicit=True`), so the server starts with zero secrets loaded and no diagnostic. `onetool serve` / root `onetool --config` now fail with an actionable "Secrets file not found" message pointing at `onetool init`, matching the existing missing-config failure pattern. `onetool init validate` gets the same explicit check for a user-supplied `--secrets` path.
- `onetool init` prints an explicit "next step" hint (`onetool init validate --config <path>`) after a successful write, making `init validate` the documented, tool-reinforced verification step end to end.
- Docs (`README.md`, `docs/learn/quickstart.md`, `docs/learn/installation.md`) are rewritten around the single recommended sequence: bootstrap install → `onetool init` → `onetool init mcp-config` → `onetool init validate`, with the manual `uv tool install` path kept as an explicit alternative. `onetool init --help` text is updated to state the same idempotency/overwrite contract the docs describe.

## Capabilities

### New Capabilities
- `onetool-install-flow`: the bootstrap installer script contract (platform detection, uv bootstrap, extras selection, checksum/inspect-first verification, pinned-tag mirror) and the documented end-to-end repeatable first-run command sequence (install → init → mcp-config → validate).

### Modified Capabilities
- `onetool-cli`: adds the `onetool init mcp-config` subcommand (ADDED requirement); changes non-interactive `onetool init` from unconditional overwrite to idempotent no-op plus `--force` override (MODIFIED "Init Guided Setup" requirement); adds an explicit startup failure message when `--secrets` points at a nonexistent file (MODIFIED "CLI Entry Point" requirement).

## Impact

- Affected code: `src/onetool/cli.py` (`init_app` gets a new `mcp-config` command; `init_callback` gets `--force` + idempotency + a post-write validate hint; `_load_runtime_config` gets an explicit secrets-missing branch), `src/ot/config/secrets.py` (`get_secrets` gains an `explicit` passthrough parameter), `src/ot/config/loader.py` (`load_config` passes `explicit=secrets_path is not None` into `get_secrets`).
- New files: `scripts/install.sh`, `scripts/install.ps1` (canonical bootstrap scripts, versioned in git so a tag-pinned GitHub raw URL always serves the version that shipped with that release), plus a `just` recipe that copies them into `docs/` (and generates `.sha256` checksums) so `mkdocs build`/`mkdocs gh-deploy` serves them from the documented domain.
- Docs affected: `README.md:53-85` (Install section), `docs/learn/quickstart.md` (steps 2, 3, 6), `docs/learn/installation.md:37-73,146-167` (Install + MCP Configuration sections), plus a new "Other clients" section built from `onetool init mcp-config`'s own output.
- Tests affected/added: `tests/unit/core/test_init_redesign.py` (idempotency/`--force` cases), `tests/unit/core/test_cli_runtime_modes.py` (missing-secrets startup failure), a new `tests/unit/core/test_init_mcp_config.py` (per-client output shape).
- **Dependency — extras value used in docs/scripts:** the bootstrap's default extras set and every "recommended install" doc snippet use `onetool-mcp[all]`. The *meaning* of `[all]` (currently `util+dev`, excluding `scrape` and `whiteboard`) is being changed by `p16-extras-restructure` (folds `whiteboard` into `[util]`, deletes the standalone `[whiteboard]` extra, keeps `all = util+dev`). This change does not itself edit `pyproject.toml` extras — it only ever writes the literal string `onetool-mcp[all]`, so it is correct regardless of which change lands first, and automatically inherits p16's fix once it lands.
- **Dependency — secrets step:** `onetool init mcp-config` reads (but does not create or populate) `secrets.yaml` at the resolved config-dir path. Creating/guiding the secrets file itself (the "Set up encrypted secrets?" TUI step, `ot_secrets.set`/`get`) is owned by `p14-guided-encrypted-secrets`. This change composes with whichever init path (TUI-driven or `ensure_ot_dir`) p14 converges on: it only checks `<config-dir>/secrets.yaml` existence at print/startup time and does not duplicate secrets creation logic.
- No changes to `pyproject.toml` extras, `ot_secrets.py`, or any file owned by `p14`/`p16`/`p18`.

## Context

V3's #1 priority move (per `wip/release-v3/release-v3-report-2.md` Executive Summary) is "make install seamless." Two concrete gaps block that today:

1. **No one-command install.** The documented path is `uv tool install onetool-mcp[all]` followed by manually hand-editing `onetool.yaml`/`secrets.yaml` paths into MCP client JSON that every doc currently hard-codes as a placeholder (`README.md:75`, `docs/learn/quickstart.md:87`, `docs/learn/installation.md:157` all show `/Users/yourname/...` or `/path/to/...`). Only Claude Code is documented, despite OneTool working with any MCP client (`README.md:20`).
2. **No single "is this repeatable" contract.** `wip/release-v3/issues/repeatable-install-and-config-flow.md` documents that install, `onetool init`, `onetool init validate`, secrets placement, overwrite behavior, and startup failure guidance exist as separate doc fragments with no stated idempotency or overwrite contract. Verified against `src/onetool/cli.py` at `main`@`151a52b3` (2026-07-04):
   - `onetool init` non-interactive mode (`init_callback`, now at `cli.py:382-480`, non-interactive branch at `:477-480`) *unconditionally* calls `_write_onetool_yaml(config_path, [])` — an empty includes list — every time it runs, silently discarding any previously-selected extensions and backing the old file up to `.bak` with no confirmation and no opt-out. This is not idempotent and not "the CLI cannot express the contract" — it is a bug the current CLI has the pieces to fix (a `--force` flag, checked before writing).
   - `onetool serve --secrets <path>` (and root `onetool --config ... --secrets ...`) silently ignore a `--secrets` path that does not exist: `ot.config.loader.load_config` (`src/ot/config/loader.py:455`) calls `get_secrets(secrets_path, reload=True)` without `explicit=True`, so `ot.config.secrets.load_secrets` (`src/ot/config/secrets.py:71-75`) takes its "return `{}`, log at debug level" branch instead of its already-implemented `explicit=True` → `raise FileNotFoundError` branch. The server starts successfully with zero secrets loaded and no diagnostic — the exact "expected failure message when startup cannot find required config or secrets" gap the issue calls out.

**Anchor drift found (flagged per instructions, not silently fixed):** the issue file (`wip/release-v3/issues/repeatable-install-and-config-flow.md:50-54`) cites `src/onetool/cli.py:247` (init), `:296` (TTY overwrite prompt), `:342` (non-interactive), `:348` (`init validate`), `:577` (missing-config startup check). At `main`@`151a52b3` the actual line numbers are `:382-480` (`init_callback`), `:431-437` (TTY overwrite prompt), `:477-480` (non-interactive branch), `:483` (`init validate`), `:712-733` (`root_callback` missing-config check) — roughly 130-140 lines later throughout, consistent shift suggesting unrelated commits landed above these functions since the issue was filed. The line *content* and behavior described are still accurate; only the numbers moved. This design and the specs use the verified current line numbers.

## Goals / Non-Goals

**Goals:**
- One documented, copy/paste command that gets a clean machine from "nothing installed" to "MCP client connected and `ot.status()` works," with `uv` preserved as the underlying package manager (never replaced by a frozen binary).
- A CLI command that prints correct, resolved, client-specific MCP JSON for the four most common clients, ending the hand-edited-placeholder-path problem.
- A first-run contract precise enough that `onetool init --help`, the docs, and the actual CLI behavior all agree, with the disagreement points (idempotency, overwrite, startup secrets failure) fixed rather than merely documented as-is where the fix is small and self-contained.

**Non-Goals:**
- Packaging `onetool` as a frozen/standalone binary (PyInstaller) — evaluated and rejected; see the "Bootstrap installer script" spec requirement for the full rationale (worker-pool `uv run` dependency, extras model, sign/notarize burden).
- The guided encrypted-secrets TUI step inside `onetool init` (creating/populating `secrets.yaml` interactively, `ot_secrets.set`/`get`) — owned by `p14-guided-encrypted-secrets`. This change only ever *checks whether `secrets.yaml` exists* at a resolved path; it never creates or writes secret values.
- Changing what `[all]`/`[util]`/`[dev]`/`[whiteboard]`/`[scrape]` extras actually contain in `pyproject.toml` — owned by `p16-extras-restructure`. This change only ever writes the literal string `onetool-mcp[all]` into scripts/docs.
- Printing HTTP-transport (Streamable HTTP) client config from `mcp-config` — the existing `onetool-cli` spec already documents stdio as the recommended local mode and HTTP root mode as a "pure MCP client URL config" case for containerized clients; `mcp-config` covers the stdio/command-based case that all four target clients (Claude Code, Claude Desktop, Cursor, VS Code) use by default for locally-run servers. Out of scope for this change.
- A benchmark/CI job that actually drives a live Claude Desktop/Cursor/VS Code instance end to end — the "clean-machine flow" scenario is verified by a documented manual test procedure (see tasks.md Verification), not new browser/process automation.

## Decisions

**D1 — `onetool init` non-interactive idempotency is a CLI behavior fix, not just documentation.** The issue's "Suggested cleanup" lists this as a decide-and-document item, and explicitly says "Do not introduce a new install wrapper unless the current CLI cannot express the contract" (which is about *installers*, not about this specific `init` bug). Silently discarding a user's previously-selected extensions on every re-run is exactly the kind of "install pain" V3 targets, the fix is a five-line existence check plus a new `--force` flag (a pattern `ensure_ot_dir`'s own `force` parameter already establishes elsewhere in the same file), and it directly enables the "`onetool init` run twice is a no-op the second time" verification the wave-map task calls for. Fixing it beats documenting a bug as intended behavior.

**D2 — Thread `explicit=True` for CLI-supplied `--secrets`, don't invent a new error path.** `load_secrets(secrets_path, explicit=True)` already raises `FileNotFoundError(f"Secrets file not found: {secrets_path}")` — the only problem is nothing calls it with `explicit=True` from the CLI-facing `load_config`/`get_secrets` chain. Adding an `explicit: bool = False` parameter to `get_secrets` and passing `explicit=secrets_path is not None` from `load_config` (`loader.py:455`) is the minimal fix: it changes behavior only when a user explicitly passed `--secrets <path>`, and preserves every other caller (`tool_loader.py:414` calls `get_secrets()` with no args; unaffected). `_load_runtime_config` in `cli.py` already has a broad `except Exception` around `get_config(...)` that prints `[red]Error loading config:[/red] {e}` and writes to `serve.log` — the new `FileNotFoundError` naturally flows through that existing path with a clear, specific message; no new exception-handling machinery is needed at the CLI layer beyond making sure the message text points at `onetool init` (see tasks.md).

**D3 — `mcp-config`'s `command` field resolves `onetool` via `PATH`, not a bare string.** Every existing doc (`README.md:74`, `quickstart.md:86`, `installation.md:156`) hard-codes `"command": "onetool"`. This works when the MCP client inherits the invoking shell's `PATH`, but is a known failure mode for GUI-launched clients (Claude Desktop in particular is commonly launched without shell rc files sourced, so a `uv tool install`-installed binary's shim directory may not be on its `PATH`). Resolving to the absolute path via `shutil.which("onetool")` at the time `mcp-config` runs removes an entire class of "client can't find the command" support issues, and is exactly what "resolved paths (no placeholders)" in the task brief calls for applied to the `command` field, not just `--config`/`--secrets`.

**D4 — VS Code gets its own JSON shape (`servers` + `"type": "stdio"`), not a copy of the `mcpServers` shape.** Verified against current VS Code MCP documentation: VS Code's `.vscode/mcp.json` (or user-profile `mcp.json`) uses a top-level `servers` key (not `mcpServers` like Claude Code/Desktop/Cursor) and requires an explicit `"type": "stdio"` field per server entry. Printing the wrong key name would silently fail to register the server in VS Code — `mcp-config` must special-case this client rather than reusing one shared template for all four.

**D5 — Bootstrap script's `onetool init` step runs non-interactively; the script says so rather than trying to fake a TTY.** `curl -LsSf <url> | sh` (and `irm ... | iex`) means the *script's* stdin is the pipe from `curl`/`irm`, not the user's terminal — so any `onetool init` invocation inside the script observes non-TTY stdin regardless of how the user's shell is configured, and correctly takes the non-interactive path (a documented, tested branch — see D1). Trying to work around this (e.g. reopening `/dev/tty`, prompting for flags) is unnecessary complexity for a V3-scope bootstrap; the simpler and more honest design is to run the minimal non-interactive init, then print a closing instruction to re-run `onetool init` interactively for extension/secrets selection. This composes cleanly with `p14`'s future guided-secrets TUI step without this change needing to know anything about it.

**D6 — Bootstrap scripts live in `scripts/` (versioned, tag-pinned via GitHub raw) and are mirrored into `docs/` for domain hosting, rather than living only under `docs/`.** A single canonical copy under `scripts/` gets tag-pinned reproducibility for free via `raw.githubusercontent.com/beycom/onetool-mcp/<tag>/scripts/install.sh` (any git tag automatically serves the script as it existed at that release, no extra release-process plumbing needed). A `just` recipe copies it into `docs/install.sh`/`docs/install.ps1` (mkdocs serves non-Markdown files under `docs/` verbatim at the same relative URL) before `docs-build`/`docs-deploy`, and generates the accompanying `.sha256` checksum files at the same time — so the docs-domain copy can never drift from the versioned source of truth.

## Risks / Trade-offs

- **[Risk] Making non-interactive `onetool init` a no-op by default is a CLI behavior change (BREAKING) for anyone scripting `onetool init` expecting unconditional overwrite.** → Mitigation: `--force` restores the old unconditional-overwrite behavior with one flag; V3 is an explicitly breaking window (maintainer rule: renames/behavior changes, not silent shims), and the new default (never silently discard a user's prior config) is strictly safer than the old one.
- **[Risk] `shutil.which("onetool")` may resolve to an unexpected `onetool` earlier on `PATH`** (e.g. a stale dev checkout or a different install) if the user has more than one on `PATH`. → Mitigation: this matches how the user's own shell would resolve `onetool` anyway (same `PATH` semantics), so `mcp-config`'s output stays consistent with what running `onetool` manually in that shell does; document this in the command's `--help` text.
- **[Risk] Bootstrap script correctness can't be exercised by `pytest`** (it's shell, not Python) so `just check` alone won't catch a broken script. → Mitigation: `bash -n scripts/install.sh` (syntax-only) is cheap and catches gross errors; the tasks.md Verification section requires an actual manual run-through on at least one clean environment before this change is considered done, and the design deliberately keeps the script's logic to five sequential, individually-testable steps (uv-present check, uv install, `uv tool install`, `onetool init`, `onetool init mcp-config`) rather than anything branchy.
- **[Risk] Two distribution URLs (docs domain + GitHub raw) for the "same" script could drift if the `docs/` copy step is forgotten before a release.** → Mitigation: the copy step is generated (part of `docs-build`/`docs-deploy`), not a manual release checklist item — see D6; a stale docs-domain copy is caught by the "Docs-domain script matches repo script" spec scenario, which tasks.md turns into a real diff check.

## Implementation guardrails

- **No compatibility shims.** Non-interactive `onetool init` re-runs are a no-op by default; there is no flag that silently preserves the *old* unconditional-overwrite-without-a-flag behavior other than `--force` explicitly passed. Do not add an env var or config toggle to opt back into the removed default.
- **No stubbing or TODO-deferral.** If `shutil.which("onetool")` resolution, the VS Code `servers`/`stdio` shape, or the bootstrap script's platform detection turns out to need a case this design didn't anticipate, stop and report it — do not print a placeholder value or silently skip a client.
- **Tests are part of every code task.** Every `cli.py`/`config/secrets.py`/`config/loader.py` change gets a `@pytest.mark.unit @pytest.mark.core` test in the existing `tests/unit/core/` suite (matching `test_init_redesign.py`'s and `test_cli_runtime_modes.py`'s existing patterns — `CliRunner().invoke(app, [...])`). `just check` (lint + typecheck + test) MUST pass before this change is considered complete.
- **Every listed `rg`/verification command in tasks.md's Verification group MUST actually be run, and MUST return the stated result.** A task that touches docs is not done until the `rg` check for stale placeholder paths returns empty.
- **Scope boundary enforcement.** Do not edit `pyproject.toml` extras (`p16`), do not add secrets-creation/TUI logic to `ot_secrets.py` or the init secrets step (`p14`), do not touch `serve-prompts`/`serve-skills`/other capability specs. If implementing this change surfaces a need to touch those files, stop and report the dependency instead of doing the other change's work inline.

# Architecture Pack v2 — Report and Rendering Design

Status: proposed design for the requirements in `arch-v3-wip/requirements.md`.

This document is a design and research record, not evidence that the layout
acceptance gates have passed. It recommends the stack to take into the required
spike. Production selection remains conditional on the fixture benchmark in
requirements section 15.

## 1. Decision summary

### Proposed production direction

| Decision | Proposed choice | Confidence | Gate before production |
| --- | --- | --- | --- |
| C4 architecture renderer | Direct `@xyflow/react` (React Flow 12) with OneTool-owned, Archify-styled custom nodes and edges | High | Accessibility, offline bundle, multi-instance, and semantic export spike |
| Layout engine | `elkjs` layered layout in a dedicated worker, wrapped by a OneTool staged layout pipeline | Medium-high | Must pass all hard geometry gates and improve the baseline congestion score by at least 30% |
| Attached diagrams | Validated, presentation-only local SVG assets generated by any external tool; no native sequence renderer in Report v2 | High | Attachment security, offline loading, viewport, accessibility metadata, and failure-state tests |
| Diagram navigation | Archify-inspired `DiagramFrame` for generated architecture views plus a reduced attachment-viewer control set | High | Keyboard/touch review and multi-instance isolation |
| Scene/export source | OneTool-owned renderer-neutral `ArchitectureScene`, never renderer DOM or React Flow state | High | SVG/PNG fidelity and transactional export tests |
| Archify use | Reference and selectively port visual tokens, architecture navigation patterns, text-fit, port-spread, and composition-checking modules | High | File-level provenance and licence inventory for every derived module |
| LikeC4 use | Renderer/layout baseline during the spike; retain the existing view-only source and source-export contracts behind a OneTool parser/serializer | High | Remove the runtime renderer/compiler packages if the proposed stack wins; do not retain a runtime fallback |
| Layout challengers | Current LikeC4/Graphviz, recursive Dagre, and MSAGL.js | High | Run identical inputs, dimensions, labels, presets, and viewport targets |

The recommended combination is not the least code in the optimistic case. It
has the lowest expected risk-adjusted effort because it gives OneTool direct
control of canonical identity, semantic DOM, exact routed geometry, interaction,
and export while delegating the difficult compound placement problem to a
layout engine built for compound graphs and ports.

No candidate-specific data is persisted. YAML/Excel, resolved OneTool state,
saved-report YAML, `ViewGraph`, and the neutral scene remain the only contracts
outside the selected renderer and layout modules.

The initial diagram experience includes:

1. **C4-style architecture diagrams** with genuine System, Application
   (container-level), and Component projections; and
2. **presentation-only local diagram attachments**, including sequence diagrams
   generated by Mermaid, PlantUML, ZenUML, LikeC4, or another external tool.

Report v2 validates and displays attached SVG assets inside the shared shell. It
does not parse, lay out, reconstruct, or claim the internal semantics of those
assets.

The C4 naming maps to the existing canonical model without adding aliases or a
second hierarchy:

| Report projection | C4 interpretation | Canonical content |
| --- | --- | --- |
| System | System Context | Users/actors, selected systems, external dependencies, and system relationships |
| Application | Container | OneTool `application` entities inside their parent systems and their interfaces |
| Component | Component | OneTool `component` entities inside their parent applications plus required surrounding context |

### Why not select unconditionally now?

Desk research cannot establish `QUAL-01`, `QUAL-02`, `QUAL-05`, `QUAL-06`, or
the P95 performance targets. The proposed stack becomes the production choice
only if the benchmark proves those properties. If it fails, the decision is
reopened before production code adopts candidate-specific types. Production
still ends with one selected C4 renderer/layout path and one generic attachment
viewer. There are no runtime fallback renderers.

## 2. Evidence and current baseline

### Repository baseline

The current implementation already has useful neutral seams and catalog
semantics:

- Python owns loading, validation, roadmap replay, selection, projection, and
  presentation resolution.
- `ViewGraph` carries canonical IDs and hierarchy.
- `SolutionLayoutResult` carries neutral node bounds and edge points.
- The frontend has bounded caches and a latest-request gate.
- Python SVG and Draw.io export consume canonical graph data plus neutral
  geometry.
- `DiagramCatalogEntry` keeps stable diagram IDs, applicability, and a variant
  list for the current implementation; Report v2 narrows runtime rendering to
  generated architecture views and presentation-only attachments.

The implementation nevertheless falls short of the new requirements:

- `LikeC4SolutionRenderer.tsx` constructs LikeC4 low-level `ComputedView` data
  using `_stage`, `_type`, and an `unknown` cast.
- Layout direction is fixed to `LR`.
- The neutral result omits ports, containers as distinct geometry, edge
  sections, label bounds, shared lanes, metrics, and structured diagnostics.
- Layout diagnostics are always empty.
- Browser layout and Python export geometry both depend on LikeC4-specific
  conversion.
- Report generation performs a per-report Vite build and requires local
  `node_modules`.

Measured with `cloc` on 2026-08-10:

| Existing area | Hand-authored code LOC |
| --- | ---: |
| `src/otdev/tools/_arch/v2/` | 7,784 |
| Frontend `src/` and build/runtime scripts | 4,854 |
| Architecture-focused Python and frontend tests | 4,837 |
| Current frontend `solution/` area | 1,437 |

These figures are context, not code-retention targets. The design reuses the
sound semantic preparation path and replaces renderer-specific and per-report
build paths cleanly.

### Archify inspection

The reviewed Archify checkout is version 2.13.0 at commit
`5875dc81b5c77c7004d7c1d297dda470fce97f50` and is MIT licensed. Its strengths
are directly relevant:

- a crisp technical visual language with coordinated themes;
- self-contained HTML, keyboard interaction, focus/reach/route concepts, and
  export techniques;
- semantic SVG hooks and accessible text;
- automatic port spreading and explicit route controls;
- substantial composition checks for overlaps, node crossings, shared
  corridors, border runs, label clearance, bend rhythm, and route stretch;
- distinct renderers for architecture, workflow, sequence, dataflow, and
  lifecycle diagrams, useful as research references rather than V2 runtime
  dependencies.

It is not a suitable whole production renderer or layout engine:

- its architecture grid module explicitly says it is fixed cell math, not
  auto-layout;
- architecture components require authored coordinates or grid cells;
- boundaries are calculated from authored members after placement;
- its JSON IR and placement assumptions would become a second diagram model;
- the standalone viewer is a 13,151-line HTML template with application-level
  state and interaction;
- the architecture/shared/checker subset alone is about 4,008 executable LOC,
  making wholesale copying a large maintenance surface.

Use Archify as a bounded source of techniques. Candidate ports should be small,
typed modules behind OneTool contracts. The highest-value reuse is its visual
grammar, semantic passport, route probe, semantic radar, navigation rail,
and mechanical composition checks. Do not adopt
its template, document format, fixed placement model, or application shell.

### React Flow inspection

React Flow supplies the interaction and rendering substrate but deliberately
does not supply layout. Its official layout guide recommends external engines
and describes ELK as the only listed option with dynamic node sizes, sub-flow
layout, and edge routing. React Flow provides:

- custom HTML nodes and exact custom SVG edges;
- per-instance providers and event APIs;
- fit, pan, zoom, controls, minimap, viewport transforms, and selection;
- focusable nodes and edges, keyboard selection, ARIA labels, DOM attributes,
  and automatic pan-to-focus;
- client-side image export examples and static/SSR support when dimensions are
  supplied;
- an MIT licence and an active TypeScript/React maintenance surface.

LikeC4 itself exposes XYFlow hooks internally, so using React Flow directly
removes a domain adapter rather than introducing an unrelated lower layer.

React Flow nodes are HTML and its edge layer is SVG. The renderer therefore
must not be used as export data. A separate neutral SVG serializer is required,
which is already required by `DATA-16` and `EXPORT-01`.

The proposed stack moves the largest layout payload into a worker and avoids

improvement, not a conclusion: only the release-mode Vite outputs count for the
decision. A candidate whose total offline assets exceed the current LikeC4
baseline by more than 25% requires an explicit performance/maintenance decision.

### LikeC4 inspection

LikeC4 remains a strong baseline:

- already integrated and pinned;
- mature architecture-specific interaction, search, focus, navigation, and
  React embedding;
- MIT licensed;
- Graphviz/WASM layout and multiple static export formats;
- custom React nodes and supported XYFlow hooks.

Its disadvantages for Report v2 are structural:

- OneTool must manufacture a LikeC4 computed model even though OneTool already
  owns the canonical model;
- current integration uses low-level fields and casts;
- Graphviz layout is coupled to the LikeC4 diagram representation;
- exact OneTool port, route-lane, label, and diagnostic contracts are not its
  public product model;
- roadmap stability, staged recursive layout, boundary stubs, and OneTool
  quality repair would have to be forced through or implemented around the
  adapter;
- the current Graphviz result is the baseline that must be beaten, not evidence
  of the required improvement.

Retaining LikeC4 as the renderer/layout stack is the lowest optimistic LOC
option, but it has the highest risk of late discovery that a required geometry
or interaction cannot be implemented without undocumented internals or
duplicated layout logic.

## 3. Target system design

```text
YAML / Excel
    -> Python load + validate + replay
    -> resolved snapshots and canonical indexes
    -> selection + projection + presentation resolution
    -> ReportPayload + saved-report YAML
    -> prebuilt offline report bundle
         -> canonical report store
         -> diagram catalogue + variant resolver
              -> C4 ViewGraph projector
                   -> LayoutRequest
                   -> dedicated layout worker
                        -> normalize + aggregate + preset
                        -> recursive ELK placement
                        -> deterministic ports + corridor routing
                        -> labels + quality checks + bounded repair
                        -> ArchitectureScene + diagnostics + metrics
                   -> React Flow architecture renderer
              -> validated local attachment catalogue
                   -> generic SVG attachment viewer
         -> shared Archify-inspired DiagramFrame
         -> architecture scene serializers -> SVG / PNG
         -> low-priority Draw.io / Confluence adapters
```

### Ownership rules

| Module | Owns | Must not own |
| --- | --- | --- |
| Python preparation | Source parsing, stable IDs, validation, replay, resolved snapshots, normalized selectors, projection semantics, presentation | Renderer IDs, viewport state, layout coordinates |
| Report store | Active report intent, active resolved state, derived rows/counts, shared selection/focus, transient view state | Source replay rules, persisted geometry |
| Architecture layout subsystem | Dimensions, placement, ports, routes, labels, bounds, geometry diagnostics | Architecture selection, roadmap replay, visual DOM |
| React Flow adapter | Viewport, event translation, semantic architecture node/edge rendering | Layout decisions, saved-report schema, export geometry |
| Attachment viewer | Safe local SVG presentation, viewport, full screen, title/description, original-file action | SVG semantic parsing, canonical selection, diagram-specific navigation |
| `DiagramFrame` | Applicable navigation, details, route/focus controls, viewport, full screen, copy link | Diagram semantics, canonical projection, layout geometry |
| Export adapters | Materializing an architecture scene into SVG, PNG, Draw.io, or Confluence payloads; publishing validated attachments unchanged | Re-projecting architecture data or reading renderer DOM |

## 4. Data and scene contracts

### Generated `ReportPayload`

The payload contains resolved data, not source deltas for the browser to replay:

- schema and application bundle versions;
- workspace/report identity and presentation tokens;
- fully resolved baseline and roadmap snapshots in a compact normalized form;
- change explanations and notes;
- canonical node/edge records and hierarchy indexes;
- selector indexes for systems, system groups, changes, change groups, and tags;
- diagram catalogue and validated local attachments;
- report-library seed entries and structured preparation diagnostics.

The browser may derive scope and detail projections from a resolved snapshot.
It must not reinterpret source delta records.

### `LayoutRequest`

```ts
interface LayoutRequest {
  schemaVersion: string
  requestId: string
  graphId: string
  selectionId: string
  stateId: string
  detail: 'system' | 'application' | 'component'
  target: { width: number; height: number; aspect: number }
  preset: LayoutPreset
  nodes: LayoutInputNode[]
  edges: LayoutInputEdge[]
  visualGroups: VisualGroup[]
  previous?: PreviousGeometry
}
```

Input nodes contain canonical ID, kind, parent, stable children, deterministic
dimensions, selected/context state, and semantic-zone hints. Input edges contain
canonical ID and member IDs, correctly oriented endpoints, direction,
integration class, status, label dimensions, and lowest common ancestor.

### `ArchitectureScene`

```ts
interface ArchitectureScene {
  schemaVersion: string
  requestId: string
  graphId: string
  selectionId: string
  stateId: string
  nodes: SceneNode[]
  containers: SceneContainer[]
  ports: ScenePort[]
  edges: SceneEdge[]
  labels: SceneLabel[]
  lanes: SceneLane[]
  bounds: Rect
  diagnostics: LayoutDiagnostic[]
  metrics: LayoutMetrics
}
```

All coordinates are absolute scene coordinates. Containers also retain their
canonical parent. Edges contain ordered sections, junction points, source and
target port IDs, arrow semantics, member canonical IDs, and optional shared
lane IDs. Labels contain explicit bounds and target IDs.

Diagnostics are structured records with code, severity, affected canonical
IDs, geometry, message, and suggested action. Human strings are a view of the
record, not the contract.

Canonical IDs remain unchanged in data and events. The renderer may derive a
safe, instance-prefixed DOM ID, but it exposes canonical identity through
`data-node-id` and `data-edge-id`.

### Attachment contract

Presentation-only diagrams use validated attachment metadata rather than a
second semantic scene:

```ts
interface DiagramAttachment {
  id: string
  title: string
  description?: string
  mediaType: 'image/svg+xml'
  ownedPath: string
  integrity: string
  intrinsicWidth?: number
  intrinsicHeight?: number
}
```

Preparation owns path validation, media-type verification, sanitization,
external-resource rejection, bundle ownership, and integrity metadata. The
browser owns only viewport and presentation state. It must not derive canonical
entities, relationships, search indexes, transcripts, or navigation from SVG
elements, classes, labels, or geometry.

### Existing diagram catalog and authored sources

Report v2 uses the diagram catalogue for generated architecture views and
validated local attachments:

- stable diagram ID, title, folder, applicability, source, and selected
  architecture view remain intact across YAML, Excel, bundles, and report state;
- non-architecture diagram outputs are included as validated local attachments,
  not native renderer variants;
- selecting an attachment does not change scope, roadmap, comparison, focus,
  or canonical selection;
- canonical-reference errors retain exact source locations;
- safe local external attachments remain presentation-only and never extend
  the canonical architecture model.

The existing pinned view-only `.c4` subset remains a supported authored input.
A bounded OneTool preparation parser replaces the current
concatenate-and-compile path. It resolves canonical `@{id}` references and the
existing allowlisted predicates, groups, notes, navigation, layout intent, and
parallel blocks into an `AuthoredArchitectureDocument`. It does not accept
LikeC4 logical model, `specification`, or deployment declarations and does not
become a general LikeC4 parser.

This keeps the authored-source contract without carrying LikeC4 model,
compiler, layout, or viewer types into the payload. Deterministic LikeC4 source
export remains a serializer from canonical OneTool data as required by the
current export contract; it is not an input to Report v2 rendering. Removing or
renaming that public format would require a separate explicit contract change.

### Versioning and cache keys

Projection and scene versions are independent. The architecture cache key
includes:

- projection schema version;
- layout schema and engine version;
- graph, selection, state, and detail identity;
- node dimensions and target aspect;
- layout preset and configuration;
- previous-geometry fingerprint when stability mode is used.

Caches are bounded by both entry count and serialized bytes. Saved-report YAML
never stores the key or geometry.

## 5. Report application

### State model

Use one reducer/store with these explicit partitions:

| State | Examples | Persistence |
| --- | --- | --- |
| Durable report intent | scope expression, hop depth, roadmap state, detail, theme, section and grid configuration | Validated saved-report YAML |
| Derived report data | effective scope, reach, rows, counts, active `ViewGraph`, change explanation | Recomputed only |
| Shared inspection | selected canonical ID, projected selected ID, focus/reach/route mode | Runtime only |
| Per-diagram viewport | pan, zoom, active search result, local tab state | Runtime only |
| Async work | active request IDs, pending/error status, cache status | Runtime only |

One action commits a roadmap or scope change. All counts, grids, projection,
selection reconciliation, and layout request identity derive from the resulting
state, preventing mixed old/new views.

### Three screens

1. **Reports** reads locally saved validated YAML records and generated seed
   reports. Each card is one keyboard-operable control.
2. **Create/Edit Scope** keeps a draft separate from committed report intent.
   Filtering and pagination never mutate committed scope.
3. **Report** uses the browser page as its scroll container. Sections are
   disclosures; diagrams have bounded canvases but no second page-level scroll.

The Solution Diagram always exposes System, Application, and Component C4
projections. Other diagrams exposes applicable authored architecture views and
validated local attachments as accessible tabs. Workflow, sequence, dataflow,
and lifecycle/transition diagrams are generated outside Report v2 and supplied
as presentation-only SVG attachments. Switching tabs preserves each mounted
instance's local viewport; shared canonical selection remains synchronized only
among generated architecture views.

AG Grid Community receives stable row and column IDs. The application/component
combined mode uses flat rows with indentation, not Enterprise tree data.
Selection uses canonical lookup maps so either grid or diagram can reveal its
counterpart without changing scope.

## 6. Layout pipeline

ELK is a kernel inside a OneTool algorithm, not a single call over the raw
graph.

### Stage 1 — deterministic dimensions and normalization

- Sort canonical peers by stable semantic order and then canonical ID.
- Validate parent/child consistency and edge endpoints.
- Flatten effective direction from interface/relationship semantics.
- Calculate every edge's lowest common ancestor.
- Use fixed design tokens and a deterministic text-wrap/measurement policy.
  Browser DOM measurement is not layout input.
- Normalize prior geometry into the current scene coordinate system.

### Stage 2 — projection simplification

- Aggregate visually equivalent parallel interfaces while retaining member IDs.
- Create boundary stubs for one-sided in-scope interfaces.
- Classify selected, context, external, actor, bus, disconnected, and ordinary
  nodes.
- Apply semantic zoom and label policy before placement, not after content has
  become unreadably small.

### Stage 3 — preset and semantic zones

The preset resolver derives direction and zones from topology:

- **System:** inbound actors, selected core, peer/support, bus, and downstream
  zones.
- **Application:** selected system containers remain dominant; external systems
  become compact perimeter containers.
- **Component:** local application layouts dominate; cross-container traffic
  uses boundary corridors and low-priority labels are deferred.

Direction is scored from flow depth, actor position, feedback edges, target
aspect, and label dimensions. It is not globally fixed to LR or TB.

### Stage 4 — recursive placement

1. Layout innermost containers independently with ELK layered or compact box
   placement for disconnected children.
2. Replace each completed container with a quotient node sized from its child
   layout and heading.
3. Repeat outward until the top-level quotient graph is placed.
4. Preserve internal coordinates when only external container relationships
   change.

The spike also tests ELK `INCLUDE_CHILDREN` for cross-hierarchy cases, but the
production mode remains the one that wins stability and congestion measures.
The design does not retain both modes as runtime fallbacks.

### Stage 5 — deterministic ports and corridors

Port identity is derived from:

```text
(owner container, peer container, semantic direction, integration class,
 visual aggregate, side)
```

Port groups are sorted by canonical keys and assigned to stable side slots.
Cross-container routes pass through owner and ancestor boundary ports. Dedicated
corridors are reserved before routing. High-fan-out buses may receive a bus
lane; unrelated traffic must not silently share it.

ELK orthogonal routing supplies initial sections where it meets the contract.
A small OneTool Manhattan corridor router handles reserved inter-container
lanes and boundary stubs. This is a deterministic post-process, not a second
general layout engine.

### Stage 6 — labels, quality checks, and bounded repair

Place labels on the longest eligible section, then check:

- node/container overlap and containment;
- edge-node and edge-heading intersection;
- proper crossings and ambiguous shared corridors;
- container-border runs;
- label-route and label-node clearance;
- bends, stretch, micro-segments, and minimum interior segments;
- aspect ratio and packing efficiency.

Port the useful ideas from Archify's geometry checker into typed,
renderer-neutral functions. Repair is bounded and local: shift a label, select
another eligible segment, nudge a corridor, or hide an optional label behind an
accessible marker. Never silently move canonical nodes after the scene has
passed containment checks. An unresolved hard failure rejects the scene.

### Stage 7 — roadmap stability

- Feed previous positions and stable model order into the next request.
- Keep unchanged child layouts intact when their local graph is unchanged.
- Prefer previous relative order unless it creates a new crossing or hard
  failure.
- Place additions near their parent and strongest neighbours.
- Normalize translation and scale before calculating displacement metrics.

React animation is presentation only. It cannot hide a geometrically unstable
result, and it is disabled for reduced-motion users.

### Stage 8 — worker and request safety

The worker owns ELK and all geometry passes. The main thread sends serializable
requests and receives serializable scenes.

- New requests supersede old request IDs immediately.
- Stale results are discarded before cache or store mutation.
- Where ELK work cannot be interrupted safely, terminate and recreate the
  worker after a debounce boundary rather than allowing stale work to publish.
- Worker readiness and layout duration are recorded separately.
- Hard-size input is rejected before transfer; warning-size work stays in the
  worker.

## 7. React Flow renderer

React Flow consumes an already laid-out `ArchitectureScene`:

- nodes use exact scene positions and sizes and are not draggable;
- invisible handles align with scene ports;
- custom edges render the exact ordered scene sections and arrowheads;
- containers use parent-relative React Flow positions derived from absolute
  scene geometry;
- labels are scene-owned overlays with stable semantic hooks;
- one `ReactFlowProvider` and instance ID is created per diagram;
- no global DOM query or singleton diagram state is allowed.

Inline report diagrams disable wheel zoom so ordinary page scrolling wins.
Explicit controls, keyboard shortcuts, touch gestures, and full-screen mode
provide navigation. Full screen enables richer canvas gestures, traps focus,
locks background scroll, fits after transition, closes on Escape, and restores
the invoking control's focus.

Nodes and selectable edges receive concise ARIA labels containing kind, name,
status, and direction. Focus, selection, reach, and route tracing combine
stroke/shape/pattern changes with colour. The overview map is derived from scene
geometry and remains available for diagrams larger than the viewport.

Search, upstream/downstream reach, and route tracing operate on canonical graph
indexes in the report store. React Flow receives only the resulting emphasized
ID sets.

## 8. Shared diagram frame and attachment viewer

### Archify visual profile

The supplied screenshots are the visual acceptance reference for generated
architecture views. Reuse the character, not the application template:

- a faint square technical grid on an off-white or deep-navy canvas;
- compact outlined nodes with rounded corners, kind icons, strong names, muted
  technology/role labels, and dashed labelled hierarchy or trust boundaries;
- a restrained semantic palette for kinds and statuses, with glow reserved for
  the active selection or route;
- clear orthogonal arrows with compact pill labels and strong directional cues;
- monospace diagram labels and metadata, paired with a readable sans-serif for
  longer explanations;
- light, floating inspection surfaces with crisp borders and shadows, used only
  when they help route reading or selected-element inspection.

Attachments keep the visual language authored by their external generator. The
report adds only neutral frame chrome and never restyles or interprets internal
SVG elements.

### Presentation-only attachment viewing

The attachment viewer consumes `DiagramAttachment` metadata and validated local
SVG bytes. It provides title, description, intrinsic-size handling, fit/reset,
pan, zoom, full screen, and download/open-original actions. Its viewport state
is local to the mounted tab.

The viewer does not inspect SVG classes, labels, element IDs, or geometry to
create report semantics. It offers no internal selection, search, passport,
route, transcript, outline, stepping, or playback. Missing, rejected, or
unsupported assets produce a visible diagnostic and recovery action.

### Shared Archify-inspired `DiagramFrame`

The supplied Archify screenshots establish the navigation target. Recreate the
patterns as owned React components rather than copying the monolithic template:

| Archify pattern | OneTool behavior |
| --- | --- |
| **Semantic passport** | Dockable/popover architecture details for the selected node or edge: canonical ID, kind, technology, tags/groups, status, hierarchy, source/change note, incoming/outgoing counts, and copy link |
| **Relationship passport** | When an architecture edge is selected, show direction, endpoints, label/type, member interface IDs, route position, and adjacent relationships |
| **Route probe** | Shortest authored architecture route with breadcrumb chips, previous/next journey controls, overview, and clear |
| **Semantic radar** | Architecture minimap derived from neutral scene geometry; attachments may use only a non-semantic viewport overview |
| **PATH / MAP / LENS modes** | PATH traces an architecture route; MAP restores the complete scene; LENS filters emphasis by kind, status, scope, integration type, tag, or owner without mutating projection |
| **READ / zoom rail** | Visible fit/reset, zoom out/in, zoom percentage, search, help, and mode controls with accessible names and shortcuts |
| **Focused-route dimming** | Preserve the complete architecture diagram as context while strongly emphasizing the chosen route with non-colour cues |
| **Copy link** | Copy a fragment containing report ID, state, diagram ID, canonical selection, mode, and route; never encode source data or saved geometry |

Every `DiagramFrame` owns its DOM refs and viewport API. Multiple generated
architecture and attachment instances can coexist without global queries. The
passport and route probe apply only to generated architecture views and may
float over the canvas in full screen; inline report mode uses a compact popover
or adjacent disclosure so it does not obscure normal page reading.

Transient copied-link state is separate from saved-report YAML. Opening a link
validates every referenced canonical ID against the active generated payload;
missing IDs produce diagnostics rather than display-name substitution.

## 9. Export, packaging, and delivery

### Prebuilt offline bundle

Release engineering builds one versioned application bundle. The Python wheel
contains the bundle, local fonts/icons, worker code, licences, and an ownership
manifest. `arch.generate` copies the bundle to a staging area, safely injects or
attaches the escaped `ReportPayload`, validates the owned set, and atomically
publishes it. It never invokes npm, Vite, or Node.

The `file://` build uses no dynamic imports that fetch files. The layout worker
is emitted as an inline/blob worker compatible with the bundle CSP. Fonts and
icons are local. Build verification opens the report with networking disabled
and fails on every request attempt.

### SVG and PNG

A pure serializer emits generated architecture SVG from canonical data plus
`ArchitectureScene`:

- explicit viewBox from complete bounds;
- semantic groups and canonical data attributes;
- local theme tokens, fonts, icons, patterns, markers, labels, and legend;
- no scripts, event attributes, external references, or renderer DOM capture.

The report rasterizes that SVG locally for PNG. Python publication can use the
existing `resvg-py` dependency once the same SVG bytes are available. Validated
attachments are copied unchanged and are not regenerated from report data.

### CLI export execution gate

Browser export naturally shares the ELK worker. CLI `arch.export` still needs a
way to execute the same packaged layout entry without reinstating a per-report
frontend build. The spike must prove one of these before ELK is selected:

1. run the prebuilt offline render entry in managed local Chromium through the
   Python export harness; or
2. run the exact bundled layout module in a vetted embedded JavaScript runtime.

The first is preferred for fidelity because it exercises the production bundle.
It introduces a browser-runtime prerequisite for CLI SVG/PNG export and must be
explicitly accepted and packaged. If neither option is supportable across
target platforms, the ELK proposal fails the operational gate and direct
Graphviz becomes the leading layout candidate. There will be no hidden Node
requirement and no production fallback engine.

Python remains responsible for staging, validation, ownership checks, atomic
publication, rollback, and user-file protection.

### Draw.io and Confluence

These remain low priority. Draw.io converts architecture scenes to pages without
relayout. The Confluence static path attaches the same SVG/PNG. A later Forge
Custom UI macro bundles the same report renderer and reads validated report
data; document export selects the static representation. Neither extension may
introduce another graph projection or rendering architecture.

Presentation-only diagram attachments keep their original validated bytes for
download and publication. Report v2 does not convert them to Draw.io or recreate
them through the architecture export path.

ELK's official layered algorithm supports compound graphs, cross-hierarchy
edges, ports, edge labels, orthogonal routes, model-order strategies, and an
interactive layout mode. Those capabilities map closely to the contract, but
their actual composition quality and stability must still be measured.

Dagre is intentionally retained in the spike because it provides a transparent
simple baseline for recursive placement. React Flow's own documentation notes
an open sub-flow problem when sub-flow nodes connect outside the sub-flow and
that Dagre does not route edges, so selecting it would make OneTool own most of
the difficult geometry.

MSAGL.js is the strongest newly found challenger. It offers compound graphs,
Sugiyama placement, spline/bundled/rectilinear routing, SVG/WebGL renderers, and
an MIT licence. Its documentation also calls the project under development,
states that cancellation is currently ignored, and warns that rectilinear
routing can become slow around 90 nodes. Those points make it a benchmark
candidate rather than the default.

## 11. Benchmark and selection plan

### Spike implementations

Each C4 layout spike accepts the same `LayoutRequest` and emits the same
`ArchitectureScene`:

1. instrument the current LikeC4/Graphviz adapter and convert its output;
2. implement the proposed ELK worker pipeline;
3. implement recursive Dagre placement plus the minimum shared corridor router;
4. implement an MSAGL core adapter if its compound graph and worker packaging
   pass a one-day feasibility check.

Archify is evaluated as a quality-checking and rendering adjunct, not as an
automatic placement candidate. React Flow and the OneTool SVG serializer render
the exact same scene, so renderer fidelity can be compared without conflating
layout.

Native sequence benchmarking is not a Report v2 selection gate. The completed
ZenUML spike is preserved below as deferred research rather than work required
to select or ship the V2 architecture renderer.

### Recorded evidence

For every fixture, state, detail level, direction preset, and candidate record:

- hard geometry failures;
- all weighted quality counts per 100 visible edges;
- bounds, aspect ratio, packing efficiency, bends, stretch, and segment length;
- unchanged-node median and P95 displacement between adjacent states;
- cold worker start, warm layout duration, serialization size, and main-thread
  blocking;
- renderer frame/interaction timings and emitted asset sizes;
- SVG/PNG semantic fidelity and DOM accessibility audit;
- blind dependency, route-tracing, and roadmap-change tasks.

Keep JSON evidence and deterministic SVG/PNG artefacts under a benchmark output
directory excluded from the shipped bundle. Commit compact summaries and
representative expected fixtures.

### Deferred ZenUML evidence

The bounded ZenUML 4.2.0 spike under `react-flow-poc` records:

- valid deterministic compilation for checkout and nested 12-participant,
  100-message stress fixtures;
- browser rendering and adapter annotation of 6/6 plus 12/12 participants and
  9/9 plus 100/100 messages;
- synchronized pointer/keyboard selection, passport state, step state, radar,
  and direct reveal of stress step 100;
- a 415.98 kB minified / 131.85 kB gzip shell plus a lazy 3,458.47 kB minified /
  869.00 kB gzip ZenUML chunk;
- 1,577 × 3,615 stress SVG bounds and inadequate presentation of the deliberate
  long-label case;
- no stable public canonical IDs in emitted SVG. The spike attaches IDs through
  ZenUML class and label/order conventions, which must remain a version-pinned
  compatibility adapter rather than a saved or public contract.

This evidence is retained for work after Report v2 is complete. It does not
establish a V2 `SequenceDocument`, `SequenceScene`, renderer dependency, runtime
adapter, transcript, export path, or identity contract. For V2, ZenUML output is
equivalent to any other validated presentation-only SVG attachment.

### Selection rule

A candidate is ineligible if it:

- has any `QUAL-01` or `QUAL-02` failure;
- misses the 30% weighted improvement over current production;
- cannot meet roadmap displacement targets;
- cannot run warning-size work off the main thread;
- leaks candidate IDs/types into a public or saved contract;
- requires a per-report frontend build or hidden network/runtime service;
- cannot power both interactive and static export paths from the neutral scene;
- fails licence or distribution review.

Among eligible candidates, select lowest weighted geometry score, then roadmap
stability, P95 duration, total offline bundle size, and implementation surface,
in that order. Record the final renderer and layout decisions separately.

## 12. Verification strategy

| Layer | Tests |
| --- | --- |
| Preparation | YAML/Excel equivalence, replay, selectors, scope hops, boundary interfaces, direction, stable IDs, report YAML validation |
| Layout contracts | Architecture schema round-trip, deterministic ordering, absolute/relative coordinates, ports, sections, labels, stale request rejection |
| Geometry | Fixture metric tests, property-based containment/intersection tests, golden scene hashes, adjacent-state displacement |
| Renderer | Generated-architecture multi-instance isolation, canonical events/hooks, exact scene routes, semantic DOM, keyboard/touch/pointer behavior; attachment viewport isolation without semantic SVG scraping |
| Report | Three-screen flow, grid configuration, selection reconciliation, roadmap atomicity, save/load, responsive/reduced-motion behavior |
| Export | Architecture-scene-to-SVG golden tests, PNG bounds/fidelity, no external references, unchanged validated attachment publication, Draw.io scene reuse, transactional publication failures |
| Packaging | Wheel contains versioned bundle and licences, no Node generation path, `file://` offline test with network denied |
| Traceability | Every applicable MUST maps to a production-path test or named review gate; stale and duplicate mappings fail `just check` |

Visual regression snapshots support the geometry metrics; they do not replace
them. Accessibility combines automated checks with keyboard and screen-reader
review gates for diagram navigation and full screen.

## 13. Migration sequence

1. Freeze current LikeC4 fixture outputs, metrics, bundle sizes, and behavior.
2. Expand the neutral request/scene/diagnostic contracts and compile existing
   catalog/variant inputs into neutral authored documents without changing
   public `arch` values.
3. Build the candidate spikes and select renderer and layout independently.
4. Implement the selected C4 worker/renderer, shared `DiagramFrame`, generic
   attachment viewer, architecture scene serializers, and export harness.
5. Build the report store, three screens, grids, save/load, and shared
   selection against canonical data.
6. Replace per-report building with the versioned prebuilt offline bundle.
7. Switch production and acceptance tests to the selected path.
8. Delete the LikeC4 runtime renderer/compiler/layout packages and all other
   unselected candidate code, scripts, payload fields, and tests in the same
   change. Keep the independently implemented view-only source contract and
   deterministic source exporter. Removed values fail normal validation; no
   aliases or legacy branches remain.
9. Add Draw.io and Confluence only after the core report, SVG, and PNG path is
   accepted.

The public contract changes in this design require `/opsx:new` before
implementation.

## 14. Risks and unresolved gates

| Risk | Consequence | Mitigation / decision gate |
| --- | --- | --- |
| ELK produces technically valid but congested compound routes | Recommended layout fails core outcome | Required fixture score and blind task review before selection |
| ELK previous-position hints are insufficient | Roadmap views jump | Preserve local child layouts, stable model order, and reject if displacement gate fails |
| CLI cannot execute the packaged ELK module portably | Divergent or Node-dependent export | Prove managed-browser or embedded-runtime harness before selection |
| React Flow HTML nodes diverge from SVG export | Browser/static mismatch | Both consume one scene and shared visual tokens; cross-render golden tests |
| Shared navigation obscures inline report content | Report becomes a canvas-first app again | Compact inline mode; floating passport/route probe only in full screen; keyboard-dismissible panels |
| Attachment SVG contains unsafe or remote content | Offline/security boundary is broken | Validate and sanitize during preparation; reject scripts, event handlers, and external resources; fail visibly |
| Presentation-only attachment is mistaken for a semantic report view | Users infer unsupported selection or analysis | Label attachments clearly and expose only viewport, metadata, full-screen, and original-file actions |
| Replacing LikeC4 runtime accidentally breaks catalogued `.c4` sources or variants | Existing portable diagrams stop round-tripping | Preserve the catalog contract; parse the pinned view-only subset into neutral documents and retain source-located validation fixtures |
| Main-thread or bundle cost is too high | Offline report feels heavy | Separate worker, measure main/worker assets, compare with current LikeC4 bundle, hard projection limits |
| Archify reuse grows into a fork | Maintenance and attribution burden | Cap reuse to named modules; maintain source revision, headers, licence, inventory, and NOTICE |
| EPL obligations for ELK are missed | Distribution risk | Complete `MIG-04` review; ship required source/licence notices and do not modify vendored ELK output casually |
| MSAGL matures rapidly and outperforms ELK | Premature selection | Keep it in the one-time benchmark, not as a runtime fallback |
| Multiple Other-diagram semantics are forced into node-link rendering | Incorrect diagrams | Keep them as externally generated presentation-only SVG attachments; share only shell/viewport/full-screen/download contracts |
